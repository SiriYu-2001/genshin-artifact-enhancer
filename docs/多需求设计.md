# 一次扫描、多需求序贯强化

## 推荐使用方式

用一份任务配置描述需要培养的所有配装；`demands` 从前到后就是优先级。每个需求引用现有角色配置，继续使用自己的套装、主属性约束、平均词条权重、暴击上限和概率阈值。一个需求的身份是“角色 × 套装 × 用途”，而不是只有角色名；同一角色、同一套装但权重不同，也应有不同的需求 ID。

推荐的“优先级让装”组合为 `equipment: borrow`、`allocation: priority`。高优先级先选，低优先级让路，名单外角色的现有装备也可借用。名单外角色没有评分配置，因此只报告其装备被谁借走，不声称为其重新优化了配装。所有分配均为虚拟方案，不自动换装。

单角色单套装仍用原来的 `start --profile`。也可在多需求任务中只填写一个需求，策略与多角色使用同一套规则。

## 两个独立的策略维度

| 设置 | 行为 |
|---|---|
| `equipment: borrow` | 可使用任何角色当前装备的物品，受显式保留和高优先级占用约束 |
| `equipment: protected` | 仅使用闲置装备或该角色当前装备；未知归属不会当作闲置 |
| `allocation: priority` | 按需求优先级分配；同时使用的需求不能获得同一件物品 |
| `allocation: independent` | 每个需求独立选最优，允许冲突，并明确列出冲突；适合比较单需求上限或完全换装轮用 |

“不借用”不能单独解决冲突，因为两个角色可能都选中同一件闲置装备。想要不扒装且不冲突，使用 `protected + priority`。显式 `reserved_ids` 对两种模式都有效，且不会因分数低而取消。

## 队伍与同时使用场景

队伍用于组织需求，场景决定是否必须同时备齐。两个需求只要出现在同一场景，就不能共享物品。冲突不作传递扩展：A 与 B 同场、B 与 C 同场，并不代表 A 与 C 必须互斥。

例如两队要同时备好：

```json
{
  "version": 1,
  "equipment": "borrow",
  "allocation": "priority",
  "demands": [
    {"id": "sandrone", "profile": "../profiles/木偶.json"},
    {"id": "odetta", "profile": "../profiles/奥黛塔.json"}
  ],
  "teams": {"队伍一": ["sandrone"], "队伍二": ["odetta"]},
  "scenarios": [{"name": "两队同时备齐", "teams": ["队伍一", "队伍二"]}]
}
```

实际每队可以填写多个需求 ID。两队若允许换装轮流使用，将它们放入两个不同场景即可。场景也能直接填写 `demands`，或使用需求 ID 数组的简写。

没有指定场景时：不同角色默认不能共享，同一角色的不同用途默认允许切换复用。指定场景后，以显式场景为准，且所有需求必须被场景覆盖；因此也能要求同一角色两套配装分别保留装备。不同配置中的角色别名用于判断是否是同一个角色。

每个需求在所有场景中采用一套固定配装。若希望某个角色在不同队伍里也切换装备，应拆成两个需求；否则会对不同场景的冲突取并集。这是明确的配置含义，不把同时穿不上的几套装备合计为一个方案。

## 分配与序贯决策

每次调度执行以下步骤：

1. 从扫描快照合并所有已确认的等级、词条和装备归属更新。
2. 从最高优先级开始，为每个需求计算现有 +20 库存中的最佳合法 4+1；排除与它同时使用的高优先级需求已占用的物品。
3. 对每个需求，在上述同一可用库存中计算各胚子强化到 +20 后改善整套得分的概率区间。
4. 选择仍有达标候选的最高优先级需求，再按概率选择一件。已有单件执行器逐阶段放入、读实际结果、重算该需求的概率，直到停手或满级。
5. 将真实结果写回共享库存，从步骤 2 重新开始。低优先级培养出的结果可能让高优先级出现新候选，不能把高优先级任务永久标记为“已完成”。

概率条件仍是各需求自己的 `P(改善整套分数) >= threshold`，没有把各角色的分数直接相加。A 停养的 +8 胚子仍可被 B 接续培养，物品身份和状态不会复制。相同一件的随机结果在不同需求之间相关，本版没有使用 `1 - ∏(1-p)` 这样的独立事件近似。

一件培养完后，重新分配能够形成 A 用新花 → A 原花给 B → B 原花给 C 的链条。程序记录占用变化并发布完整的新方案；实际装备归属始终单独保存，不会把“虚拟分配给 B”写成“游戏中已被 B 装备”。

优先级是硬顺序，没有用某个看似很大的权重去近似。高优先级的提升可能压低低优先级的最终分数，这在让装模式下是允许的，报告不会隐藏这种损失。缺少完整 +20 基准的需求标为 `missing_mature_build`，不以 0 分伪造基准，也不自动把任意胚子拉满。

## “最优”的范围

当前实现是**按优先级依次求单需求最优的贪心分配**，不是完整的联合全局最优求解器。单需求继续使用现有保守内部数值边界计算，展示分数使用游戏显示值。

一个反例：A 对装备 x、y 都得 10 分，B 对 x 得 10 分、对 y 得 0 分。如果 A 的同分选择恰好取 x，B 会受损，尽管让 A 取 y 完全不影响 A。当前算法不承诺把这类同分选择也做全局优化。

若后续需要严格的优先级全局最优，应联合求解所有需求的物品分配：每部位选一件、套装与主属性合法、同场景每件物品最多分给一个需求、暴击计分封顶。先最大化最高优先级得分，固定其最优值后再优化第二个，依此类推。不能在进入这个联合求解器前按单角色分数删除“被支配”的物品，因为物品的不同身份会影响其他角色的分配。

建议先使用目前清晰、可复现的优先级模式。队伍伤害、充能硬门槛、最低配装保障、同分联合优化属于另一层目标，不能隐含在用户现有的线性副词条权重中。

## 库存复用和持久化

扫描只在任务启动时执行一次。所有需求共用同一 `scan_directory` 和一个 `inventory-updates.json`，不为角色创建互相隔离、逐渐过期的库存副本。物品 ID 由扫描 ID 与位置组成，识别目标仍校验实际属性，不依赖旧背包坐标。

每次消耗保留原来的 `pending` 与凭据机制：先写记录，再点击；未确认结果只能读取核对，不能重发消耗。多需求续跑先完成当前物品的核对，再重新调度。最终输出：

- `allocation-final.json`：各需求最终五件、套装、主副属性、实际装备者、分数、让装关系、共享关系和场景。
- `RESULTS.md`：可读配装表和让装清单。
- `allocation-history.jsonl`：每次重新分配产生的占用变化。
- `summary.json`、`plan.json`：状态、候选、边界不确定项与未配齐项。

这是一轮受控任务内的复用，不是永远信任旧库存。玩家在任务外新增、分解、强化、重置或换装后，应重新扫描。`--scan` 只应复用当前有效的快照；若旧快照之后有本程序的强化记录，离线规划同时传 `--updates`。人工保留 ID 也只适用于对应扫描；不在本次扫描中的保留 ID 会报错，避免静默失效。跨扫描的稳定身份匹配与增量识别尚未实现。

## 可视化配置器的接口

规划器与游戏执行器已经分离，网页不需要 LLM 或 Computer Use。下一步的本地配置界面可以提供：

1. 需求卡片：角色、套装、用途、主属性、权重、暴击上限、阈值；拖拽调整优先级。
2. 队伍与场景：将需求放入队伍，选择哪些队伍必须同时备齐，哪些允许换装轮用。
3. 离线预览：各需求得分、相对独立最优的损失、冲突、让装清单与五件装备明细。
4. 本地执行状态：扫描中、定位中、强化中、结果待确认、完成；暂停与续跑。

配置器只读写同一 JSON 格式，由本地串行执行器操作游戏。网页尚未实现；本次交付配置、离线规划、报告和多需求调度，不把页面原型当作已经运行的功能。

## 命令与验证边界

```powershell
# 一次新扫描，执行所有需求
python -m enhancer campaign start --config campaigns/优先级让装.json

# 中断后的同一任务续跑，不重新扫描
python -m enhancer batch

# 离线预览，无游戏输入；同时输出 JSON 和同名 Markdown
python -m enhancer campaign plan --config campaigns/优先级让装.json --scan <扫描目录> --updates <库存更新JSON> --output <输出JSON>

# 仍保留单角色单套装模式
python -m enhancer start --profile profiles/奥黛塔.json --ownership borrow
```

多需求优先级方案是依次分配，不保证全队联合最优。网页可选择培养结束后自动穿戴；五星素材始终禁止。
